# Beignet v0.1

v0.1 is an experimental, public developer preview of a durable agent runtime.

Its promise is deliberately small:

> Submit an agent turn, disconnect, and let an eligible worker finish it.
> Control state survives a leader change, and immutable artifacts can live on
> a local filesystem or in an S3-compatible object store.

## Architecture

Beignet has three logical roles and two server-side programs:

- **Head**: a disposable TypeScript client that starts or watches a session.
- **Control plane**: a small Go/Raft cluster that owns step state, claims,
  leases, fencing, ordering, and accepted result references.
- **Worker**: a TypeScript/Pi process that pulls eligible steps, executes them,
  and offers a result plus an optional next step to the control plane.

Workers are clients of the control plane. They are not required to be Raft
members and are not paired one-to-one with a control node.

Large immutable bytes do not belong in Raft. They are stored through an
`ArtifactStore` implementation:

- `filesystem` for a single-node development setup or a genuinely shared
  filesystem;
- `s3` for a shared S3-compatible service. SeaweedFS is the v0.1 self-hosted
  integration target.

## Identity

v0.1 keeps these identities separate:

- **artifact hash**: SHA-256 of immutable bytes;
- **step id**: a unique logical invocation, reused only when retrying that
  invocation;
- **attempt**: the fencing generation for one execution attempt;
- **session id**: the conversation containing the step.

Content identity does not imply execution identity. Two requested LLM samples
with identical inputs must be able to execute independently.

## Artifact publication

The publication order is:

1. Verify the bytes against their artifact hash.
2. Store the bytes in the configured artifact store.
3. Commit the artifact's hash and size to Raft.
4. Only then submit or commit a step value that references the artifact.

If storage succeeds and the Raft commit fails, an unreferenced object may be
left behind. That is safe. Garbage collection is later work. Specs and results
are opaque to the control plane, so custom clients share responsibility for
never committing a reference before its bytes are stored successfully.

## Execution guarantee

Execution is **at least once**. Raft accepts at most one result for the current
fenced attempt, and it inserts that result's next step atomically with the
accepted result.

This does not make external tool side effects exactly once. A tool can change
the outside world and crash before its result commits. Retriable tools need an
idempotency key, a downstream transaction, or a compensation strategy.

## Delivered surface

- Correct Raft snapshot persistence and restore.
- Logical step ids that do not collapse independent samples.
- Correct working-directory propagation through a whole turn.
- Trustworthy leader-forwarding and leader-failover tests.
- Filesystem and S3-compatible artifact stores behind one interface.
- No artifact bytes in Raft entries or snapshots.
- Pull-based TypeScript workers.
- Claim renewal, attempt fencing, and worker-loss recovery.
- Simple exact-match worker eligibility labels.
- Session submission and watch commands.
- A one-command local development path.
- A SeaweedFS-backed cluster example.
- Public CI, quickstart documentation, architecture documentation, security
  limitations, and release notes.

## Validation gates

- The filesystem artifact-store contract passes.
- The same contract passes against SeaweedFS through its S3 endpoint.
- A head submits a turn and exits before the turn finishes.
- A separate worker completes the turn.
- After a worker dies, its lease expires and another eligible worker can retry.
- A result from an expired attempt is fenced out.
- After the Raft leader dies, a client using a surviving follower can submit
  again after election.
- Snapshot and restart preserve steps, node metadata, artifact metadata,
  ledger time, and sequence state.
- Go tests, TypeScript tests, end-to-end tests, and the documentation build all
  pass.
- The documentation states the at-least-once and private-network-only limits.

## Not in v0.1

- Partitions or multiple Raft groups
- Kafka compatibility
- Fan-out, joins, or general DAG workflows
- RL training
- Artifact garbage collection
- Presigned uploads or direct browser access to object storage
- Multi-tenancy, billing, or a hosted control plane
- A web control dashboard
- Public-network security
- Exactly-once external side effects

## Development rule

Each behavior change starts with a plain-English invariant and a failure test.
Changes to the public contract update code, tests, and documentation together
before the release is tagged.
